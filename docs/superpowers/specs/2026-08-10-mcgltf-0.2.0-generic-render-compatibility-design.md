# MC glTF Exporter 0.2.0 Generic Render Compatibility and OBJ Export Design

## 1. Background

After the initial export verification of 0.1.0 in a real modded environment on Minecraft 1.21.1 and NeoForge 21.1.244, three kinds of boundary cases appeared:

1. Create block entities that use Flywheel GPU instancing output 0 vertices during capture and were therefore replaced by magenta placeholders.
2. The Touhou Little Maid model geometry and UVs were complete, but the runtime skin is not on a standard resource manager path, so the texture read failed.
3. glTF 2.0 can only store point, line and triangle topology, so the Blender import cannot directly keep Minecraft's original quads.

The real verification report came from a client instance containing Create 6.0.10, Flywheel 1.0.6 and Touhou Little Maid 1.5.3. The report recorded 17 `BLOCK_ENTITY_ZERO_VERTICES`, involving `FluidTankRenderer`, `GearboxRenderer` and `BracketedKineticBlockEntityRenderer`; it also recorded `TEXTURE_READ_FAILED` for the runtime block atlas and the maid skin.

The goal of 0.2.0 is to establish a generic compatibility layer for render backends while keeping the export client-side, selection-based and Blender-editable, and to generate glTF and OBJ together on every export.

## 2. Design goals

### 2.1 Must implement

- Upgrade the mod version to `0.2.0`.
- Keep the Minecraft 1.21.1 and NeoForge 21.1.244 minimum compatibility baseline.
- Every `/mcgltf export <name> [confirm]` generates glTF and OBJ together.
- glTF keeps the standard triangle topology and continues to pass validation.
- OBJ exactly preserves the original `QUADS` from the capture source, and other topologies are safely converted to triangle faces.
- Ordinary blocks are grouped by section and material in OBJ; block entities, entities and placeholders stay independent objects.
- Treat the static block model and the additional block-entity rendering as two composable parts of the same world object.
- When the static body succeeds and the additional Renderer outputs 0 vertices, no placeholder is generated.
- Establish a render-backend-level compatibility scope, supporting Flywheel 1.x in the first version, without special cases per Create block or Renderer type.
- The texture read covers, in order, resource files, CPU dynamic textures and loaded GPU textures.
- When capture and readback fail, restore all backend and OpenGL state and record stable diagnostics.
- Compatibility and completeness take priority over the real-time frame rate during export.

### 2.2 Explicitly not done

- 0.2.0 does not implement a complete OpenGL draw-call interceptor.
- The private model formats of Create, Touhou Little Maid or other mods are not parsed one by one.
- Create or the maid mod is not made a hard runtime dependency.
- No speculative coplanar merging or N-gon reconstruction is done on the original triangle faces.
- Restoring objects generated entirely by shaders with no CPU fallback geometry is not promised.
- The original coordinates, selection, unloaded chunks, cancellation, soft limit and output directory policies are not changed.

## 3. Root cause analysis

### 3.1 Flywheel zero vertices

Flywheel provides a GPU instancing path that replaces Minecraft block entity and entity rendering. Several Create Renderers return early when `VisualizationManager.supportsVisualization(level)` is true, and the geometry is submitted through Flywheel's instance data and custom shaders, so the current `CapturingMultiBufferSource` sees no vertices at all.

These Renderers also keep a non-Flywheel `VertexConsumer` fallback path. During capture, temporarily making the backend report as off and then calling the Renderer already registered by the game yields the current object's CPU geometry without parsing Create's specific model classes.

### 3.2 Fluid tank false duplication

The static shell of the fluid tank is captured from the `BakedModel`. The Renderer of an empty tank, a non-controller tank or a tank without additional visible content can legitimately output 0 vertices. 0.1.0 treated any zero output of a block entity as a failure and generated a placeholder, producing the visual result of "another copy outside the body".

The placeholder decision must combine the static model and the additional Renderer paths, and cannot be made by `BlockEntityCapture` alone.

### 3.3 Missing runtime textures

0.1.0 read CPU pixels only for `DynamicTexture`; every other `AbstractTexture` went back to the `ResourceManager` to look up a PNG. The block atlas and the skins of external model packs may already be uploaded to the GPU without a matching resource manager file, so the model and UVs are fine while the image degrades to a checkerboard.

The last generic data source of the texture chain should be the current OpenGL texture object, not a specific mod's file directory.

### 3.4 glTF face topology limit

The core primitive modes of glTF 2.0 contain only points, lines, triangles, triangle strips and triangle fans, with no quads or N-gons. The OBJ `f` can express four or more vertices, so 0.2.0 uses dual-format output to meet the two goals of transport compatibility and Blender polygon editing.

## 4. Overall architecture

### 4.1 `ObjectCaptureOrchestrator`

This component is responsible for combining the capture results of one world object:

1. Capture the static `BakedModel`.
2. Capture the fluid geometry.
3. Capture the block-entity additional Renderer inside the compatibility scope.
4. Merge the geometry, counters and diagnostics of the three paths.
5. Decide, from the complete result, between success, partial success, a legitimately empty additional render, or a placeholder.

The block entity capture layer only reports geometry and execution results and no longer generates placeholders itself. An entity has no static block body, so the unified result policy still generates an entity bounding-box placeholder when all capture paths fail.

### 4.2 `RenderFallbackRegistry`

The core defines a backend-agnostic scope interface:

```text
detect the current runtime environment
→ save the backend state
→ enter the fallback rendering scope
→ call the registered Renderer
→ restore the backend state in finally
```

The registry picks an available adapter by priority. When there is no adapter an empty scope is used, keeping the existing standard capture path.

### 4.3 Flywheel 1.x adapter

The Flywheel adapter only recognizes the Flywheel backend API and state, and does not read the Create registry, block IDs, PartialModels or Renderer classes. It uses runtime class detection and does not load the related implementation when Flywheel is not installed.

Adapter requirements:

- Save the current backend object.
- During the current Renderer call, switch to Flywheel's off backend so that `supportsVisualization` returns false.
- Support nested scopes, restoring only when the outermost one exits.
- Restore the original backend through `finally` on any exception path.
- Run only on the client render thread.
- Do not reset, destroy or rebuild the current world's Flywheel VisualizationManager.

This adapter layer is a render-backend compatibility module. All mods that use Flywheel and keep a fallback Renderer benefit automatically.

### 4.4 `TextureAcquisitionChain`

The texture chain consists of independent Providers:

1. `ResourceTextureProvider`: reads the original PNG of the resource pack.
2. `DynamicTextureProvider`: reads the CPU `NativeImage`.
3. `GpuTextureReadbackProvider`: reads back RGBA8 from level 0 of a loaded OpenGL texture.
4. `MissingTextureProvider`: generates a stable checkerboard and records the failure.

A Provider returns a unified `TextureImage`, a source type and diagnostics. Each export builds its own cache, deduplicated by resource ID, GL ID, size and content hash; old GPU IDs are not reused across exports after a resource reload.

### 4.5 Dual-topology scene layer

The current `PrimitiveAccumulator` converts all source topologies to glTF indices immediately when sealing. 0.2.0 keeps in the intermediate layer:

- The original `PrimitiveMode`
- The original-order vertex stream
- The material reference
- Object and grouping information

The background Writers each perform:

- glTF: convert to glTF-legal topology by the existing rules.
- OBJ: every four vertices of a quad make one quad face; every three vertices of triangles make one triangle face; Strip and Fan are safely expanded into triangle faces.

The intermediate layer does not merge faces across original primitives, materials or UV seams.

## 5. Data flow

```text
client world object
  → ObjectCaptureOrchestrator
  → BakedModel / Fluid / Renderer replay
  → SourcePrimitive + ObjectCaptureOutcome
  → background write queue of capacity 2
      → Streaming glTF Writer
      → Streaming OBJ/MTL Writer
  → shared TextureRegistry
  → Report Writer
  → OutputTransaction commit
```

Each object is captured only once. glTF and OBJ consume the same `SourcePrimitive`, ensuring consistent pose, material, UV and diagnostics. Outside the thread-safety boundary, the Writers only handle immutable scene values and never access the client world or OpenGL.

GPU readback and Renderer replay happen on the client render thread. The user has confirmed that export completeness comes first, so these steps may occasionally exceed the original 6 ms tick budget; background file writing still uses a bounded queue of capacity 2.

## 6. Object result and placeholder rules

| Static model | Additional rendering | Final result |
|---|---|---|
| Has geometry | Has geometry | Both parts are exported together |
| Has geometry | 0 vertices | Only the static body is exported, no placeholder is generated |
| No geometry | Has geometry | The additional rendering result is exported |
| No geometry | 0 vertices | A placeholder is generated and the failure is recorded |
| One path throws, the other succeeds | The successful part is kept and a partial degradation is recorded |
| All paths throw | A placeholder and complete failure diagnostics are generated |

A legitimate zero output and a failure must be distinguished: a Renderer that returns normally but has no vertices is empty; a Renderer that throws an exception, a backend scope failure or invalid topology is failed.

## 7. GPU texture readback

### 7.1 Execution steps

1. Get the current `AbstractTexture` and GL ID from the `TextureManager`.
2. Verify that the texture object exists and has a 2D base mip level bound.
3. Query the level 0 width, height and readable format.
4. Save the current active texture, 2D texture binding, pack alignment and related pixel-transfer state.
5. Read back the RGBA8 pixels.
6. Restore all saved GL state.
7. Validate the size and byte length, and deduplicate by content hash.
8. Generate a PNG and register it in the shared texture table.

### 7.2 UV rules

- Standalone entity textures keep the original UVs submitted by the Renderer.
- When a whole runtime atlas is read back, atlas UVs are kept and no sprite-local normalization is performed.
- The atlas sprite of a `BakedQuad` still goes through the existing sprite extraction path and is normalized into the exported standalone sprite PNG.

### 7.3 Failure handling

After a GPU readback failure a checkerboard is generated, recording the texture ID, GL ID, size, Provider, exception type and error message. A failure must not change the texture binding used by subsequent game rendering.

## 8. OBJ and MTL output

### 8.1 File layout

```text
mcgltf-exports/<name>/
├─ <name>.gltf
├─ <name>.bin
├─ <name>.obj
├─ <name>.mtl
├─ report.json
├─ textures/
│  ├─ minecraft/
│  ├─ <modid>/
│  └─ generated/
└─ materials/
   └─ *.json
```

### 8.2 OBJ grouping

- Ordinary blocks create an `o` per section and a `g` per material.
- Each block entity instance creates its own `o`.
- Each ordinary entity instance creates its own `o`.
- Each placeholder instance creates its own `o`.
- Object and group names use stable, predictable escaping rules.

### 8.3 Faces and indices

- Output `v`, `vt`, `vn` and `f v/vt/vn`.
- An original quad outputs a four-index face.
- An original triangle outputs a three-index face.
- Strip and Fan are expanded into triangles.
- Coordinates use `(X,Y,Z) → (X,Y,-Z)`.
- After the coordinates are mirrored the winding is adjusted in step, so the front faces and normal directions of glTF and OBJ agree.
- OBJ uses globally increasing indices, the Writer maintains offsets in streaming fashion and never rewrites historical vertices.

### 8.4 MTL mapping

- The base color texture is written to `map_Kd`.
- Transparency uses `d`, and `map_d` may be written when a separate transparency map exists.
- Emissive color is written to the common `Ke` where possible.
- Double-sidedness, blending and Minecraft-specific semantics that standard MTL cannot express continue to be written to `materials/*.json`.
- glTF and OBJ share the same set of PNGs and no textures are copied.

## 9. Output transaction and cancellation

`.gltf`, `.bin`, `.obj`, `.mtl`, textures, material sidecars and the report belong to the same transaction. The official directory is committed only after all core Writers have finished, the internal validation has passed and the report has been written successfully.

On cancellation or failure:

- Stop accepting new batches.
- Let the Writers finish their current uninterruptible write and exit.
- Close all streams.
- Restore the render backend and GL state.
- Keep the existing failure-scene policy and never commit a fake-success directory.

## 10. Diagnostics and report

The report continues to record stable object IDs, world positions, Renderer classes and exception types. New diagnostic codes:

- `RENDER_BACKEND_FALLBACK_USED`
- `RENDER_BACKEND_FALLBACK_FAILED`
- `AUXILIARY_RENDERER_EMPTY`
- `GPU_TEXTURE_READBACK_USED`
- `GPU_TEXTURE_READBACK_FAILED`
- `PARTIAL_OBJECT_CAPTURE`
- `OBJECT_CAPTURE_FAILED`

The 0.2.0 report should be able to distinguish: standard capture success, backend fallback path success, GPU texture readback success, a legitimately empty additional render, partial object degradation and a final placeholder.

## 11. Test design

### 11.1 Unit tests

- All branches of the object result decision matrix.
- The placeholder count is 0 when the static body succeeds and the additional render is empty.
- Backend scope restoration behavior in the normal, exception, nested and not-installed states.
- The same quad generates two triangle faces in glTF and one quad face in OBJ.
- Safe expansion of Strip and Fan.
- Winding and normal consistency after coordinate mirroring.
- OBJ global vertex, UV and normal indices and grouping.
- MTL material, transparency and texture relative paths.
- Texture Provider priority, caching, content deduplication and failure degradation.
- GL state restoration when GPU readback succeeds and when it throws.
- The output transaction is not committed when either of the two Writers fails.

### 11.2 Development test mod fixtures

Add:

- A block entity whose static model succeeds and whose additional Renderer legitimately outputs 0 vertices.
- A Renderer that outputs zero when a simulated acceleration backend is on and outputs quads after entering the fallback scope.
- An entity that has only a GPU texture, with no PNG in the resource manager.
- An object that is fully GPU-only and has no fallback path.

The fixtures verify the generic interfaces and do not depend on Create or the maid mod.

### 11.3 Real-mod acceptance

Environment:

- Minecraft 1.21.1
- NeoForge 21.1.244
- Create 6.0.10
- Flywheel 1.0.6
- Touhou Little Maid 1.5.3
- Blender 5.2

Acceptance criteria:

- Gearbox shafts and power parts are exported in their pose at capture time.
- A tank with liquid keeps its actual liquid level.
- Empty tanks and non-controller tanks generate no wrong placeholders.
- The 17 Create placeholders in the original verification scene drop to zero.
- The maid skin is output as a valid PNG, with no checkerboard on the model and correct UVs.
- `minecraft:textures/atlas/blocks.png` can be exported through GPU readback.
- After the OBJ is imported into Blender, the original block quads stay four-sided faces.
- glTF passes the internal validation and the Khronos Validator.
- After the export Flywheel works normally, with no lasting black blocks, vanished objects or render state pollution.
- The production JAR does not contain the development test mod.

## 12. Compatibility statement

The generic compatibility scope of 0.2.0 is:

- Standard `BakedModel`s.
- Block entity and entity Renderers that output through a `VertexConsumer`.
- Mods that use a supported acceleration backend and keep a CPU fallback Renderer.
- 2D textures already loaded into OpenGL and readable back.

Objects that are generated entirely by shaders, have no CPU fallback geometry, or use an unknown private GPU pipeline may still degrade to placeholders. This boundary must be stated clearly in the README and the report, and the wording "absolutely compatible with all mods" is not used.
